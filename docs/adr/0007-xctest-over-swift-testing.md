# ADR-0007: XCTest over Swift Testing

**Date**: 2026-08-26
**Status**: accepted
**Deciders**: rizky mashudi

## Context

`Tests/ContentSyncKitTests/` holds the XCTest stub generated by `swift package init`, and the
Example app's unit and UI tests are XCTest as well.

The package is built with the Swift 6.2 toolchain, which ships Swift Testing as the first-party
framework. But the toolchain version and the deployment floor are separate decisions, and the
deployment floor here is **iOS 15**, chosen so the SDK reaches the install base that production
apps in this space actually support. XCTest is the framework supported across that whole floor.

## Decision

XCTest throughout — package tests and Example app tests alike. `TESTING.md` documents one
framework, with no boundary for contributors to track.

## Alternatives Considered

### Alternative 1: Swift Testing for the package, XCTest for the Example app's UI tests
- **Pros**: Parameterised tests and async assertions without XCTest ceremony; aligns with where
  the platform is heading.
- **Cons**: Two frameworks in one repository; contributors must know which boundary they are on;
  availability does not extend cleanly to an iOS 15 floor.
- **Why not**: The floor is the binding constraint. A framework the deployment target cannot
  rely on is not a real option, whatever the toolchain supports.

### Alternative 2: Raise the deployment floor to match the toolchain
- **Pros**: Unlocks Swift Testing and every other recent platform API.
- **Cons**: Cuts the addressable install base sharply, which defeats the point of shipping this
  as a distributable SDK.
- **Why not**: Reach is a product requirement here, not a detail to trade away for test ergonomics.

## Consequences

### Positive
- One test framework across the whole repository.
- Large body of existing XCTest reference material.
- Test strategy — fakes conforming to repository protocols, deterministic fixtures, suites
  mirroring layers — is unaffected by the choice.

### Negative
- Class-based tests, more ceremony around async and actor isolation than `@Test`/`#expect`.
- The repository is deliberately behind the platform default on this one axis.

### Risks
- **Divergence grows as Swift Testing matures.** Mitigation: revisit when the deployment floor
  next moves; the migration is mechanical and the test strategy ports unchanged.

## Relationship to ADR-0003

ADR-0003 chose async/await over Combine. That is not in tension with this record: structured
concurrency back-deploys to iOS 13, so it is available at the iOS 15 floor. Swift Testing is not.
